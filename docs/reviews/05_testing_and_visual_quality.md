# Can the current tests tell whether a presentation is good?

**24 November 2026 · Revision `44ab332` · Assessment of the release checks and the existing sample outputs**

**The framework is useful for software regressions and insufficient for approving decks that people will present.** All 146 tests passed locally. A controlled slide with a white headline on a white background earned the same 97.2/100 as its readable counterpart. In the actual sample outputs, a board slide has three empty cards, an investor slide assigns the same percentage to four incompatible quantities, and a brand slide shows the speaker’s delivery instructions as a quotation. These are distinct failures of legibility, meaning and audience awareness. A single design score conceals which one needs fixing.

## Testing the grader itself

I held the five-slide executive plan fixed and gave the production DOM audit five simple local HTML pages. I changed only slide 2 in each run, collected the real Chromium warnings, and passed them to the production deterministic scorer. The last row is a positive control for a defect the detector was designed to catch.

| Change on slide 2 | Browser warning | Deck score | Result |
| --- | --- | ---: | --- |
| Black headline on white, baseline | None | 97.2 | Pass |
| White headline on white | None | 97.2 | Pass |
| Paragraph positioned across the headline | None | 97.2 | Pass |
| Headline reduced to 8 CSS pixels | `FONT_TOO_SMALL` | 97.2 | Pass |
| Text forced into a four-pixel-high card | `OVERFLOW` | 91.2 | Fail |

This isolates **two independent defects**. Invisibility and overlap escaped detection. Tiny type was detected, then lost when the scorer reduced warnings to overflow. The overflow case still earned a letter grade of A while failing its gate. A consumer reading just the score or grade would miss the failure.

In a separate content test, the executive fixture’s supported “48% YoY Growth” was replaced with “999% Banana Yield.” Both plans passed at 97.2. The scorer receives plan structure and word counts, so an unrelated claim with the same shape survives. This is an inexpensive regression case for a future source-aware gate. ## How I would judge visual quality

The [presentation quality testing plan](../evals/presentation_testing_plan.md) turns these findings into fixture definitions, acceptance criteria and release decisions.

**First make objectively broken outputs fail.** For each release fixture, keep a small brief, explicit required claims and units, protected presenter-only text, expected slide IDs and required output formats. Render via the public CLI. Inspect PDF text and coordinates, PPTX objects and relationships, and a presentation-client rendering of the PPTX. Count required fields on the correct slide, compare their visible values, and check occlusion, blank required regions and composited contrast. Record measured coverage per slide and format. A skipped render or missing measurement should surface as **unmeasured**. Required failures should set the release command’s exit code. Keep existing fast tests on each change.

**Then ask whether the slide communicates.** Give a reviewer the intended reader, the brief, and the final slide at presentation size. Start with three questions: *What is the main claim? What evidence on the slide supports it? What should this audience understand or do next?* Ask for the exact region that helped or obstructed the answer. Ask separately whether hierarchy, image choice and wording reinforce the message. A large green latency number is easy to see but supplies no evidence for a reliability headline. Airy space works on the brand cover but fails an investor who expects traction evidence. These distinctions make reviewer comments actionable without forcing every deck into one visual style.

**Calibrate automation against actual editorial decisions.** Begin with the board, brand and pitch failures above, their corrected counterparts, and good slides such as the brand cover. Include acceptable alternatives so a new brand style does not fail simply for changing pixels. Have a designer and an audience representative independently review shuffled pairs, record severity and reasons, then resolve disagreements. Hold out entire briefs or templates when assessing a vision judge. Measure how many known serious defects it misses and how often it rejects an acceptable redesign. Give it the source, audience, rendered pixels and neighboring slides. Use its findings for triage until it demonstrates agreement on unseen material. Screenshot diffs can point a reviewer to a change. An approved baseline and a task-based rubric determine whether the change improved the deck.

**First acceptance milestone.** On one board deck and one startup deck, require every agreed metric to survive in PDF and client-rendered PPTX. Seed four faults: wrong unit, missing card content, invisible title and leaked note. Require the appropriate check to catch each fault, and keep the approved originals passing. Publish per-slide evidence and reviewer disposition with the run. Once this works, extend the same process to brand narrative, engineering diagrams, and native-template handoff. Until then, a green run supports merging changes covered by its assertions. Presentation readiness still needs inspection of the files the user will open.
