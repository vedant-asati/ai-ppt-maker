# AI Presentation Agency Multidimensional Engineering Review

**24 November 2026** · Reviewed revision `9e22972` · [Review plan](project_review_plan.md) · [Technical findings](code/03_technical_findings.md) · [Verification record](03_verification.md)

**Release verdict.** Continue using the tool for controlled, human-reviewed drafts. Hold public distribution of the current branch, the advertised grounded-research workflow, and general-purpose PowerPoint handoff until the respective blockers are addressed. A local six-slide PDF workflow worked, and editable PowerPoint text survived a mechanical edit. Other valid inputs produced missing data, incorrect source attribution, visible speaker notes, or mismatched artifacts. A green 142-test suite did not detect these outcomes. [Verification record](03_verification.md) · [Release blockers](code/03_technical_findings.md#release-blockers)

The strongest direction is **source material to a reviewable deck**. Give the presenter a stable plan they can inspect and approve, then produce repeatable artifacts from that plan. The current emphasis on visual variety is worthwhile, but reliable drafting depends more on preserving facts and user intent than on increasing the number of layouts or image providers.

## Product usefulness and development rationale

| Workflow | Where it helps | What determines whether it saves work |
| --- | --- | --- |
| Executive with approved notes | The CLI can turn a known narrative into slides and speaker notes, and the user can revise the blueprint before rendering. | Quantities, caveats, and the requested decision must survive. One incorrect metric can cost more time to discover and correct than the draft saves. |
| Technical presenter with structured source | Reusable blocks and local replay can standardize internal briefings, especially recurring ones. | Facts near the end of documents, units, diagrams, and explanatory notes must survive. Typed charts and tables should outrank an image if precision or editing matters. |
| Presenter starting with a topic | A fast outline and a set of potential layouts can reduce the blank-page problem. | Treat the output as a draft. The model has little evidence and the user has to validate substantive assertions. |
| Presenter assembling a sourced briefing | Retrieval can identify material worth reading. | Search snippets and slide-position footnotes cannot establish claim support. This workflow needs a claim-to-evidence review step. |
| Team handing off an editable deck | Standard PPTX lets a recipient edit native text and notes, and a user-owned master could preserve branding. | Content, placement and citations must agree with the PDF, and native templates must either fit the input or reject it explicitly. |

The strongest fit is a technical operator preparing a recurring or internal deck from approved notes. That user can use the CLI and inspect the saved plan. A deck recipient often opens only the PDF or PPTX, so corrections in a plan, warning logs, or speaker notes cannot compensate for misleading visible content. The review exercised the generation and editing mechanics with fixtures. Presenter time savings, customer demand for a UI, and collaboration value still require a timed user task. [Public workflows](../../README.md#L90) · [Showcase decks](../../examples/README.md) · [Workflow evidence](03_verification.md#workflow-coverage)

The original design choices have a sound rationale. Pydantic gives generation a typed vocabulary. HTML and Chromium take visual placement out of the model's hands. A companion notes file can carry detail that would overwhelm a slide. These choices lose force when each consumer interprets the same slide differently. A template that adds its own actions or a PowerPoint exporter that places text independently is effectively a second author. Preserve creative freedom in the layout and copy stages while requiring explicit ownership of every visible claim. ## Architecture and modularity

| Boundary | Contract in use | Assessment |
| --- | --- | --- |
| CLI → config and input | Arguments, YAML, files, environment variables | Package folders are organized by domain. Most orchestration, config overrides, artifact lifecycle, and error reporting still live in `main()`. An invalid typed config can fall back to a permissive dictionary. The effective configuration varies by entry point and makes a future UI harder to implement consistently. |
| Input and research → planners | Source text, uploaded file handle, or research dossier | Each planner ingests material differently. Long and multimodal inputs can reach different stages with different fidelity. `Citation` exists at slide level, but there is no shared evidence contract with stable claim IDs. |
| Planners → `MasterPlan` | Typed slides and content blocks | This is the best architectural seam. The current schema leaves cardinality, stable IDs, layout compatibility, and some content limits to consumers. Validation mutates inputs and can renumber duplicate slides without restoring the missing content. |
| Plan → imagery and design | Theme tokens, prompt text, per-slide manifest | Provider fallback and procedural gradients are sensible. Theme resolution, provider policy, and cache identity depend on mutable run state. Theme and layout choices can silently change art direction or cache reuse. |
| HTML → browser → refinement | Files, viewport, DOM warnings | Reusing Chromium across passes is a good improvement. Numeric positions and screenshot files are available, yet exported text still has its own coordinate map. Re-rendering directly into the final HTML path makes candidate edits difficult to reject cleanly. |
| Raster and vector renders → artifacts | Ordered filename lists and boolean return values | The boundary loses slide identity and output completeness. PDF, PowerPoint, and notes can all describe a different subset of the same run while their filenames imply they match. |

Changing one layout currently touches schemas, prompt vocabulary, a multi-agent allowlist, validator rules, Jinja, hard-coded PPTX positions, tests, and sometimes scoring. Hero Statement renders in HTML, disappears during staged planning, and fails in PPTX when given a valid subtitle. A small shared layout registry could describe valid variants, visible fields, supported block types, and renderer capabilities. Keep distinct renderer implementations where fidelity requires it and make their differences testable. [CLI](../../ppt_maker/cli.py) · [Typed schema](../../ppt_maker/core/schemas.py#L158) · [Staged allowlist](../../ppt_maker/planning/multi_agent/stages.py#L45) · [Export layout positions](../../ppt_maker/export/pptx_exporter.py#L41)

My recommended shape is a callable generation pipeline with an immutable request and a run-owned directory. Give slides stable IDs and a separate display index. Keep evidence and notes attached to those IDs. Have renderers return records containing slide ID, geometry, diagnostics, and files. Exporters should return actual paths and covered IDs. A publish step can then compare the artifact set with the request and expose a clear success, degraded, or failed result. This can start around the existing `MasterPlan`, Jinja, and exporters with a small manifest. A more general framework would add migration cost before addressing the failures. ## AI behavior and factual quality

The single-shot planner can see a long source directly and attach supported files to a provider request. That makes it the better-supported default for an opt-in draft. It still truncates very long text and can continue after an upload failure. In staged planning, a source-tail claim reached single-shot but appeared in neither the architect nor the batch prompt. The architect sees an initial excerpt and the batch sees the thesis and directives. A two-slide batch returned duplicate IDs without recovery, and recovery can output business metrics without source data. A successful schema parse says little about whether the deck is true or complete. [Planner input](../../ppt_maker/planning/planner.py#L322) · [Batch prompt](../../ppt_maker/planning/multi_agent/stages.py#L379) · [AI checks](03_verification.md#planning-and-grounding)

The staged design has a real potential advantage on deep decks if the narrative plan carries an evidence map. As implemented, a 10-slide deck schedules one architect call and five synthesis batches before retries, whereas single-shot starts with one request. Parallelism can shorten some waits, but every added call widens the surface for malformed output and mismatched claims. A better experiment would compare **one planning call plus deterministic layout assignment** with both existing modes. It tests whether gains come from the semantic outline, from the extra inference, or from controlled layout selection. Add per-slide evidence retrieval before testing longer sources. [Batch size and scheduling](../../ppt_maker/planning/multi_agent/stages.py#L338)

Research and factual review should answer three separate questions. Did retrieval find a usable source? Does the quoted excerpt support the claim? Did that claim and citation survive in the final artifact? The current workflow can attach an unrelated clickable link and still pass the first question. Verify support before rendering, preserve claim IDs through compression, and abstain where a required value or source is missing. Keep estimated values visibly tagged when the user supplies them as assumptions. Design defaults should either leave empty space, change layout, or request missing material. Invented metrics and presentational filler are poor substitutes for truthful omissions. ## Visual design, implementation, and editing

The new asymmetric split produces a genuinely different composition, and Hero Statement has a useful job as a thesis or transition slide. Both would benefit from conservative defaults. On the reviewed modern-proposal deck, the mapped background asset contained a high-detail phone mockup and lettering. Repeating it behind unrelated content made headlines harder to read. A decorative layer should remain subordinate to foreground text. Choose quiet backgrounds by default, reserve expressive art for sections that need it, and test contrast against the rendered composition. A local fixture showed the underlying layout review can report no DOM findings despite poor visual balance. [Background asset selection](../../ppt_maker/design/theme_resolver.py#L24) · [Audit](../../ppt_maker/audit/quality_checker.py#L340) · [Artifact observations](03_verification.md#browser-and-export-results)

The copy rules aim to improve generic headlines and crowded slides. A fixed word ceiling misses the relationship between text, script, layout, and reading distance. The validator examines legacy bullets for density while a typed block held 80 words without a warning. Likewise, `hero_statement` accepts typed content the template ignores. Budget visible lines and layout slots, keep numbers and qualifiers intact, and treat character length as a helpful signal. Give agenda and section titles explicit semantic roles so an action-title heuristic can make room for them. [Validator](../../ppt_maker/planning/validator.py#L83) · [Hero template](../../ppt_maker/templates/hero_statement.html#L99)

Keep the raster plate plus native text output as an explicit trade-off. It delivers useful text editing and preserves effects that are hard to recreate in OOXML. It freezes backgrounds, graphs, and decorative elements and can fail when the two renderers disagree on geometry. Use existing `data-pptx-target` hooks to test whether measured browser boxes improve simple overlays. Use native shapes and charts for users who need deep edits, with a narrower supported layout set. The native master path should map known placeholder IDs in an approved template, because heuristics based on font size and position can select an unintended text element. ## Reliability, cost, and evaluation

The early remediation fixed specific symptoms. Cloudflare rejects the corrupt fixture and writes a valid PNG from JPEG. All nine selected textures resolve from the installed wheel. Planner backoff is capped between requests. The remaining reliability work requires clear end-to-end boundaries. A slow in-flight request can outlast the nominal deadline. Two runs can write the same build and cache paths. An image opted out in one configuration can still be generated because nested config fields are ignored. Provider selection and data egress should be resolved once per run and applied to planning, web research, image matching, image generation, fonts, and AI audit. [Remediation status](03_verification.md#prior-review-findings)

The tested six-slide offline control took **21.22 s cold** and **18.97 s warm** with audit and two export formats. Three browser passes took roughly five seconds each on the original fixture. In a local run without inference, rendering is the best-supported optimization target. Preserve the ability to collect browser warnings, but skip an audit screenshot when the audit needs only DOM metrics. Measure before adding parallel rendering, which could increase contention and make failures harder to attribute. A known empty cache and a warm cache need separate baselines. [Timing and artifact sizes](03_verification.md#browser-and-export-results)

The offline scorecard provides regression coverage for structure. The current **9 wins and 1 tie** come from synthetic plans. Empty audit lists and fixed token counts make the score and cost unsuitable as evidence of rendered quality or live economics. Separate missing from zero in metrics and make failures part of the denominator. Measure evidence fidelity, layout and legibility, editability, and time to an acceptable deliverable independently. Treat supported factual claims as a requirement for passing. An LLM judge can help triage language and narrative once calibrated, subject to human review of contentious outcomes. ## Feature disposition and next investments

| Feature or direction | Disposition | Evidence that should change the decision |
| --- | --- | --- |
| Typed saved plan and basic vector PDF | Core workflow after integrity checks | A clean checkout and installed wheel preserve plan intent and produce one verified page per expected slide. |
| Single-shot planning and speaker notes | Default for provider-enabled draft generation, with explicit review before sharing | Source-derived claims and notes-only content are retained in their intended visibility and output scope. |
| Web research and staged planning | Experimental | Research passes claim-level evidence tests. Staging shows a repeatable benefit on at least one deck class in paired live runs with matched models and inputs. |
| Hero, split, and rich cards | Feature work after end-to-end contracts | Each advertised layout passes PDF and PPTX fixtures for its canonical and edge variants with no introduced or lost content. |
| Generated imagery and LLM refinement | Explicit opt-in | Each improves acceptance or visual readability against local assets under measured latency and cost budgets. Offline policy and failure reporting are verified. |
| Native PPTX templates | Opt-in for user-supplied known masters | An undersized or incompatible template gives a clear result, while supported masters retain the required content and attribution. |
| Web UI, Google Slides, and other exporters | Defer until the core workflow is repeatable | User trials identify a workflow the CLI cannot serve, and the core can be called without duplicating orchestration or creating shared build state. |

1. **Protect publication and content.** Address credential history and asset provenance. Fix slide identity, output atomicity, the Hero PPTX crash, unrelated citations, invented metrics, and notes appearing on slides. Gate releases with real exported fixtures for each failure.
2. **Make the best workflow repeatable.** Make saved plans portable, honor nested configuration, enforce offline behavior, and consolidate the small set of layout and artifact contracts. Add installed-package and headless browser checks to CI as separate jobs.
3. **Measure before expanding the product.** Run a short editing trial on an executive brief, technical deck, and research deck. Give each participant the same brief and rotate the order of assisted and manually templated tasks. Record setup time, substantive edits, time to an accepted deck, evidence defects, and whether a second presenter can use it. Test planner structure and visual changes separately. A reviewable, trustworthy draft is the product outcome. Additional automation should improve that outcome under a known budget.
